# 07. Requisitos no funcionales

## 1. Enfoque de definición

Los requisitos no funcionales de EcoRuta-Wanka se definen como **escenarios de calidad** siguiendo la estructura Fuente → Estímulo → Entorno → Artefacto → Respuesta → Medida, clasificados según las características de calidad de **ISO/IEC 25010** y complementados con el modelo de escenarios de calidad de **arc42**. Queda prohibido expresar un RNF mediante adjetivos sin umbral cuantitativo (p. ej. "rápido", "seguro", "fácil de usar"); toda medida debe ser SMART y verificable mediante prueba, métrica de monitoreo o auditoría.

---

## 2. Catálogo de escenarios de calidad

| ID | Categoría ISO 25010 | Escenario de Calidad (Fuente → Estímulo → Entorno → Artefacto → Respuesta → Medida SLA) |
| --- | --- | --- |
| **RNF-01** | Eficiencia de desempeño | **Fuente:** Operador solicitando el cálculo de rutas. **Estímulo:** Petición de optimización de rutas para los pedidos pendientes del día. **Entorno:** Operación normal, hasta 150 pedidos y 15 vehículos simultáneos. **Artefacto:** Módulo del motor de optimización (VRPTW/Green VRP). **Respuesta:** Calcular y retornar un conjunto válido de rutas. **Medida:** Latencia ≤ 45 segundos en el percentil 95 (P95) para el escenario máximo definido; ≤ 30 segundos para una re-optimización dinámica (RF-07). |
| **RNF-02** | Seguridad | **Fuente:** Atacante externo o interno no autorizado. **Estímulo:** Intento de inyección SQL/NoSQL, XSS o acceso sin token válido a un endpoint de la API. **Entorno:** Producción, backend FastAPI expuesto a Internet. **Artefacto:** API REST y capa de autenticación (RF-10). **Respuesta:** Rechazar la petición, no exponer datos, registrar el evento en el log de auditoría. **Medida:** 0% de vulnerabilidades críticas u altas explotables del OWASP Top 10 en las pruebas de seguridad realizadas antes de cada entrega de iteración; 100% de endpoints protegidos que exigen token válido. |
| **RNF-03** | Usabilidad — Accesibilidad | **Fuente:** Conductor o bodeguero con nivel de alfabetización digital básico. **Estímulo:** Uso del "modo conductor" o del formulario de preferencias desde un smartphone de gama media/baja. **Entorno:** Operación diaria en campo, posible conexión 2G/3G. **Artefacto:** Interfaz web (frontend React). **Respuesta:** Renderizar la interfaz de forma perceptible, operable y comprensible. **Medida:** Cumplimiento de WCAG 2.1 nivel AA verificado mediante auditoría automatizada (Lighthouse/axe) con puntaje de accesibilidad ≥ 90/100 en las vistas del "modo conductor". |
| **RNF-04** | Adecuación funcional — Exactitud | **Fuente:** Administrador consultando el dashboard de sostenibilidad. **Estímulo:** Solicitud de cálculo de distancia, combustible estimado y CO₂ evitado de una ruta completada. **Entorno:** Operación normal, con datos de vehículo (tipo, consumo) y ruta ya registrados. **Artefacto:** Módulo de cálculo de indicadores de sostenibilidad (RF-05, RF-06). **Respuesta:** Calcular los indicadores aplicando las fórmulas y factores de emisión definidos (RN-002). **Medida:** Desviación ≤ 5% entre el valor calculado por el sistema y el valor de referencia validado manualmente en el conjunto de casos de prueba. |
| **RNF-05** | Usabilidad — Satisfacción y facilidad de aprendizaje | **Fuente:** Conductor o personal administrativo en pruebas de aceptación. **Estímulo:** Primer uso del sistema sin capacitación previa extensa. **Entorno:** Sesión de prueba de usabilidad supervisada, dispositivo real del usuario. **Artefacto:** Interfaz completa del sistema, en particular el "modo conductor". **Respuesta:** Completar las tareas clave (ver ruta asignada, reportar incidente, marcar entrega) sin asistencia externa. **Medida:** ≥ 90% de los usuarios de prueba obtienen un puntaje de usabilidad ≥ 4/5 en la encuesta SUS simplificada aplicada al finalizar la sesión (O5 del Acta de Constitución). |
| **RNF-06** | Fiabilidad — Disponibilidad | **Fuente:** Infraestructura en la nube (hosting del backend/Firestore). **Estímulo:** Corte eléctrico o caída de conectividad en una zona periférica, o caída del servicio en horario operativo. **Entorno:** Operación 5:00 a.m.–10:00 p.m., todos los días. **Artefacto:** Backend FastAPI y base de datos Firestore. **Respuesta:** El sistema debe permanecer accesible o degradarse de forma controlada (modo offline-first en el cliente) sin pérdida de datos ya sincronizados. **Medida:** Disponibilidad ≥ 99.5% mensual durante el horario operativo; RPO ≤ 5 minutos para datos sincronizados desde el modo offline. |
| **RNF-07** | Adecuación funcional — Cumplimiento normativo | **Fuente:** Operador asignando conductores a rutas. **Estímulo:** Intento de asignar una ruta a un conductor cuya jornada acumulada del día excede el límite legal. **Entorno:** Operación normal, planificación diaria de rutas (RF-08). **Artefacto:** Módulo de asignación de conductores. **Respuesta:** Bloquear la asignación que incumpla la Ley N° 30224 y sugerir un conductor alternativo disponible. **Medida:** 0% de rutas asignadas que excedan la jornada máxima legal, verificado en el 100% de los casos de prueba de asignación. |
| **RNF-08** | Mantenibilidad | **Fuente:** Equipo de desarrollo. **Estímulo:** Necesidad de corregir un defecto o incorporar un nuevo parámetro de ruteo (p. ej. un nuevo factor climático). **Entorno:** Ciclo de desarrollo iterativo (Scrum/Kanban adaptado), repositorio con frontend y backend separados (CO-03). **Artefacto:** Código fuente del backend (FastAPI) y del motor de optimización. **Respuesta:** Aislar el cambio sin afectar módulos no relacionados, mediante la separación de capas ya adoptada. **Medida:** Cobertura de pruebas unitarias ≥ 70% en los módulos de reglas de negocio y motor de optimización; tiempo estimado de incorporación de un nuevo parámetro de ruteo ≤ 3 días-persona. |
| **RNF-09** | Portabilidad — Compatibilidad | **Fuente:** Conductor o Administrador accediendo desde distintos dispositivos. **Estímulo:** Apertura del sistema desde un navegador móvil (Android, gama media/baja) o de escritorio. **Entorno:** Uso real en campo y en oficina. **Artefacto:** Frontend web (React/Vite), diseño responsivo. **Respuesta:** Renderizar correctamente la interfaz sin pérdida de funcionalidad crítica. **Medida:** Funcionamiento correcto verificado en los 2 navegadores móviles y 2 navegadores de escritorio de mayor uso reportado por los usuarios de prueba, sin errores bloqueantes. |
