## 1. Objeto del documento

Consolida las restricciones del proyecto en una **matriz multidimensional**, tomando como referencia el mapa de requisitos no funcionales **RNF-01 … RNF-09** del documento 07 (desempeño, seguridad, usabilidad, mantenibilidad, disponibilidad) y los requisitos funcionales **RF-03, RF-05, RF-07, RF-10** del documento 06. Se distinguen:

| Tipo | Significado |
| --- | --- |
| **R** — Restricción actual | Limitación vigente verificada en el código/entorno |
| **RG** — Riesgo | Escenario de incumplimiento derivado de una restricción |
| **MI** — Mitigación implementada | Mecanismo que **ya existe** en el repositorio |
| **MP** — Mitigación propuesta | Acción **no implementada**, recomendada para futuras iteraciones |

## 3. Restricciones destacadas y su verificación real

| Restricción | Estado en el código (verificado) |
| --- | --- |

| R-10 (optimización por distancia) | `RutaService` = Haversine + vecino cercano + 2-opt (sin metaheurísticas) |
| R-14 (sin autenticación) | No hay código de login/tokens; solo Admin SDK del backend |
| R-17 (dependencia Firebase) | Repositorios implementan interfaces (puertos) desacopladas |
| R-18 (credenciales fuera de Git) | `.env.example` versionado; service key ignorada |

## 5. Conclusión

Las restricciones que determinaron la arquitectura fueron: **presupuesto académico limitado** (LCC, R-05, CO-07 del doc. 04), **cero infraestructura propia** (R-06/R-07/R-11) y **alcance académico con equipo pequeño** (R-13). La respuesta implementada fue Firestore serverless, un backend desacoplado por puertos/adaptadores y validaciones de dominio orientadas a RN-004/005/006 como mitigaciones de salud y seguridad del transporte. Las restricciones relativas a autenticación, tráfico, reportes y metaheurísticas permanecen como oportunidades en versiones futuras y se registran explícitamente como **no implementadas**, sin confundirlas con funcionalidad existente.
