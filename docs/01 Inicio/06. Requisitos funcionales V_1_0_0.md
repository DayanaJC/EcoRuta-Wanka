## 1. Propósito

Este documento define los requisitos funcionales principales del sistema **EcoRuta Wanka**. Estos requisitos describen las funciones que debe proporcionar el sistema para apoyar la gestión de vehículos, pedidos, rutas, conductores, clientes y los indicadores de sostenibilidad de las operaciones de reparto.

Los requisitos están relacionados con las épicas e historias de usuario utilizadas en Jira para mantener la trazabilidad entre los requisitos y la planificación del proyecto.

---

## 2. Criterios utilizados

Los requisitos funcionales se presentan de forma individual y verificable. Cada requisito contiene:

* Identificador.
* Nombre.
* Descripción.
* Usuarios relacionados.
* Prioridad.
* Criterios de aceptación en formato Gherkin.
* Épica e historia de usuario relacionada.

Los criterios de aceptación permiten comprobar si la funcionalidad cumple con el comportamiento esperado.

# 3. Requisitos funcionales

## RF-01. Gestión de flota vehicular

**Épica:** EP-01 – Operación y gestión de recursos de reparto
**Historia de usuario:** US-001 – Gestión de flota vehicular
**Usuarios:** Administrador, Operador
**Prioridad:** Alta

### Descripción

El sistema debe permitir registrar, consultar, actualizar y gestionar la información de los vehículos utilizados para las operaciones de reparto.

La información debe permitir identificar el vehículo, conocer sus características principales, capacidad, estado y disponibilidad para una operación de reparto.

### Criterios de aceptación

**Escenario 1: Registrar un vehículo correctamente**

```gherkin
Dado que el usuario tiene permisos para gestionar vehículos
Cuando registra un vehículo con la información obligatoria válida
Entonces el sistema debe guardar el vehículo
Y debe mostrarlo en la lista de vehículos registrados
```

**Escenario 2: Actualizar la información de un vehículo**

```gherkin
Dado que existe un vehículo registrado
Cuando el usuario modifica información válida del vehículo
Entonces el sistema debe guardar los cambios
Y debe mostrar la información actualizada
```

**Escenario 3: Registrar un vehículo sin información obligatoria**

```gherkin
Dado que el usuario se encuentra registrando un vehículo
Cuando intenta guardar el registro sin completar un dato obligatorio
Entonces el sistema debe informar que falta completar la información requerida
Y no debe guardar el registro incompleto
```

## RF-02. Gestión de pedidos de reparto

**Épica:** EP-02 – Gestión de pedidos y preferencias
**Historia de usuario:** US-002 – Gestión de pedidos de reparto
**Usuarios:** Administrador, Operador
**Prioridad:** Alta

### Descripción

El sistema debe permitir registrar y gestionar los pedidos que serán atendidos mediante las operaciones de reparto.

La información del pedido debe incluir los datos necesarios para identificar el pedido, su destino, características de entrega, prioridad y estado.

### Criterios de aceptación

**Escenario 1: Registrar un pedido correctamente**

```gherkin
Dado que el usuario tiene permisos para gestionar pedidos
Cuando registra un pedido con la información obligatoria válida
Entonces el sistema debe guardar el pedido
Y debe mostrarlo en la lista de pedidos
```

**Escenario 2: Consultar y actualizar un pedido**

```gherkin
Dado que existe un pedido registrado
Cuando el usuario consulta y modifica información permitida del pedido
Entonces el sistema debe mostrar la información actualizada
Y debe conservar el estado correspondiente del pedido
```

**Escenario 3: Registrar un pedido con información incompleta**

```gherkin
Dado que el usuario se encuentra registrando un pedido
Cuando intenta guardar el pedido sin completar información obligatoria
Entonces el sistema debe mostrar un mensaje indicando los datos faltantes
Y no debe registrar el pedido
```

## RF-03. Generación de rutas optimizadas por vehículo

**Épica:** EP-03 – Motor de optimización y generación de rutas
**Historia de usuario:** US-003 – Generación de rutas optimizadas por vehículo
**Usuarios:** Operador
**Prioridad:** Alta

### Descripción

El sistema debe permitir generar una ruta de reparto para los pedidos asignados a un vehículo, considerando la capacidad disponible del vehículo y las condiciones registradas para las entregas.

La ruta generada debe presentar el orden de atención de los destinos y la información necesaria para apoyar la planificación del reparto.

### Criterios de aceptación

**Escenario 1: Generar una ruta válida**

```gherkin
Dado que existen pedidos con información de destino válida
Y existe un vehículo disponible con capacidad registrada
Cuando el operador solicita generar una ruta
Entonces el sistema debe generar una ruta para los pedidos seleccionados
Y debe mostrar el orden de los destinos de reparto
```

**Escenario 2: Generar una ruta con varios pedidos**

```gherkin
Dado que existen varios pedidos disponibles para reparto
Y los pedidos cuentan con información válida de entrega
Cuando el operador solicita generar una ruta para un vehículo
Entonces el sistema debe considerar los pedidos seleccionados
Y debe presentar una secuencia de atención de los destinos
```

**Escenario 3: Generar una ruta sin información suficiente**

```gherkin
Dado que uno o más pedidos no cuentan con información necesaria para establecer su destino
Cuando el operador solicita generar la ruta
Entonces el sistema debe informar que existen datos incompletos
Y no debe generar una ruta inválida
```

El sistema debe permitir visualizar las rutas generadas y los puntos de entrega asociados, facilitando el seguimiento de la planificación de cada recorrido.

```gherkin
Dado que existe una ruta generada

Entonces el sistema debe mostrar la ruta

```

**Escenario 2: Consultar los detalles de una ruta**


## RF-05. Indicadores de sostenibilidad

**Épica:** EP-05 – Sostenibilidad, indicadores y reportes
**Historia de usuario:** US-005 – Indicadores de sostenibilidad
**Usuarios:** Administrador, Operador
**Prioridad:** Media

### Descripción

El sistema debe permitir consultar indicadores relacionados con la sostenibilidad de las operaciones de reparto, utilizando la información disponible de las rutas y vehículos.

Los indicadores pueden incluir distancia recorrida, consumo estimado de combustible y emisiones estimadas de CO₂.

### Criterios de aceptación

**Escenario 1: Consultar indicadores**

```gherkin
Dado que existen datos registrados de rutas y vehículos
Cuando el usuario consulta los indicadores de sostenibilidad
Entonces el sistema debe mostrar los indicadores disponibles
Y debe asociarlos al periodo o información seleccionada
```

**Escenario 2: Consultar indicadores por periodo**

```gherkin
Dado que existen registros correspondientes a diferentes periodos
Cuando el usuario selecciona un periodo válido
Entonces el sistema debe mostrar los indicadores correspondientes a dicho periodo
```

**Escenario 3: Consultar indicadores sin datos**

```gherkin
Dado que no existen registros para el periodo seleccionado
Cuando el usuario consulta los indicadores
Entonces el sistema debe informar que no existen datos disponibles
Y no debe mostrar valores que no correspondan a registros existentes
```

## RF-07. Re-optimización de rutas

**Épica:** EP-03 – Motor de optimización y generación de rutas
**Historia de usuario:** US-007 – Re-optimización de rutas
**Usuarios:** Operador
**Prioridad:** Media

### Descripción

El sistema debe permitir generar una nueva propuesta de ruta cuando cambien las condiciones de los pedidos, vehículos o entregas consideradas en una ruta existente.

### Criterios de aceptación

**Escenario 1: Re-optimizar una ruta**

```gherkin
Dado que existe una ruta previamente generada
Y existen cambios en los pedidos o condiciones de reparto
Cuando el operador solicita re-optimizar la ruta
Entonces el sistema debe generar una nueva propuesta de ruta
Y debe mostrar los cambios realizados
```

**Escenario 2: Re-optimizar después de agregar un pedido**

```gherkin
Dado que existe una ruta registrada
Cuando se agrega un pedido válido que debe ser atendido
Y el operador solicita actualizar la ruta
Entonces el sistema debe considerar el nuevo pedido
Y debe presentar una nueva secuencia de atención
```

**Escenario 3: Re-optimizar sin datos suficientes**

```gherkin
Dado que la ruta no cuenta con información suficiente para realizar una nueva planificación
Cuando el operador solicita re-optimizarla
Entonces el sistema debe informar que faltan datos
Y no debe generar una propuesta inválida
```

## RF-10. Autenticación y control por roles

**Épica:** EP-06 – Acceso seguro y control por roles
**Historia de usuario:** US-010 – Autenticación y control por roles
**Usuarios:** Administrador, Operador, Conductor, Cliente/Bodega
**Prioridad:** Alta

### Descripción

El sistema debe permitir que los usuarios se autentiquen y accedan únicamente a las funciones correspondientes al rol asignado.

Los roles considerados son Administrador, Operador, Conductor y Cliente/Bodega.

### Criterios de aceptación

**Escenario 1: Inicio de sesión correcto**

```gherkin
Dado que el usuario tiene una cuenta registrada
Cuando ingresa credenciales válidas
Entonces el sistema debe permitir el acceso
Y debe mostrar las funciones correspondientes a su rol
```

**Escenario 2: Acceso a una función según el rol**

```gherkin
Dado que el usuario ha iniciado sesión correctamente
Cuando intenta acceder a una función permitida para su rol
Entonces el sistema debe permitir el acceso
Y debe mostrar la información correspondiente
```

**Escenario 3: Credenciales incorrectas**

```gherkin
Dado que el usuario se encuentra en la pantalla de inicio de sesión
Cuando ingresa credenciales incorrectas
Entonces el sistema debe informar que las credenciales no son válidas
Y no debe permitir el acceso al sistema
```

# 7. Criterios generales de validación

Los requisitos funcionales se considerarán correctamente definidos cuando:

* La función descrita pueda ser comprobada mediante una prueba.
* Los criterios de aceptación permitan determinar si el resultado es correcto.
* Cada requisito tenga una identificación única.
* Cada requisito esté relacionado con una historia de usuario.
* Cada historia de usuario esté asociada a una épica.
* Los requisitos mantengan coherencia con el alcance definido para EcoRuta Wanka.
* No existan contradicciones entre los requisitos funcionales y la planificación registrada en Jira.
