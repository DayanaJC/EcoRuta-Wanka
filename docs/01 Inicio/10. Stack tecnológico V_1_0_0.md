## 2. Metodología de evaluación

Se evaluaron alternativas **completas de stack** (no solo una pieza) en una escala **cuantitativa de 1 a 5**, donde **5 es el mejor puntaje** para el contexto de EcoRuta Wanka (proyecto académico con presupuesto limitado según CO-07 del doc. 04, equipo pequeño, orientado a la nube). Para cada criterio se define qué representa el puntaje:

| Criterio | 1 (peor) | 5 (mejor) |
| --- | --- | --- |
| **Curva de aprendizaje** | Requiere meses de experiencia (p. ej. ecosistemas con marcado verboso) | El equipo la domina en días (sintaxis sencilla, recursos abundantes) |
| **Costo de infraestructura** | Requiere servidores, licencias o capas de pago desde el inicio | Nivel gratuito amplio / costo casi nulo para un MVP académico |
| **Soporte comunitario** | Comunidad pequeña o documentación escasa | Comunidad enorme, documentación y ejemplos abundantes |
| **Escalabilidad** | Difícil escalar horizontal o verticalmente | Escalado elástico administrado (autoescalado o sin servidores) |
| **Mantenibilidad** | Estructura acoplada, cambio costoso | Separación de capas clara y pruebas automáticas facilitan cambios |
| **Rendimiento** | Lento en consultas típicas o alta latencia | Maneja la carga del MVP (RB/RC) con latencia baja |
| **Seguridad** | Mecanismos básicos o ausentes | Autenticación, cifrado en tránsito y buenas prácticas por defecto |
| **Eficiencia energética / Eco-Design** | Infraestructura siempre encendida, consumo alto | Recursos por demanda (serverless/PaaS), consumo proporcional a la carga |
| **Compatibilidad con el equipo** | Requiere aprender tecnologías ajenas al perfil | Coincide con las habilidades y el contexto académico del equipo |
| **Integración tecnológica** | Requiere adaptadores manuales entre piezas | Integración nativa entre las piezas del stack (SDK oficial) |

El puntaje total por alternativa es la **suma simple** de los 10 criterios (máximo 50). Las puntuaciones derivan del análisis del código existente y de las condiciones documentadas en los documentos 01 a 09.

### 4.1 Análisis breve por alternativa

- **A1 MERN:** ecosistema JavaScript unificado y comunidad enorme (Curva 4, Soporte 5). Mantener una base documental no relacional y un backend en Node tiene costos de operación y de seguridad no triviales (Seguridad 3), la infraestructura propia siempre encendida penaliza el Eco-Design (3) y la planificación de esquemas es más exigente (Mantenibilidad 3).
- **A2 Python/FastAPI + React + PostgreSQL:** combina el dominio de Python del equipo (Compatibilidad 4, Curva 4) con una base relacional robusta. Exige operar un servidor de base de datos (Costo 3, Eco-Design 3) y arreglos de despliegue, integración y migraciones de esquema (Integración 3), además de un adaptador SQL adicional frente a Firestore.
- **A3 Java Spring Boot + Angular:** sólido en rendimiento (5) y seguridad (5) para sistemas empresariales, pero con curva de aprendizaje alta (2), infraestructura y licenciamiento implícitos costosos (Costo 2), consumo energético alto por servidor persistente (Eco-Design 2) y poca sintonía con el perfil académico del equipo (Compatibilidad 2).
- **A4 Python/FastAPI + React + Firebase Firestore:** maximiza costo (nivel gratuito de Firebase), mantenibilidad (base administrada sin servidores), escalabilidad (autoescalado de Firestore), Eco-Design (recursos por demanda), compatibilidad con el equipo (Python + web académica) e integración tecnológica (SDK oficial Firebase Admin). Se detalla en la sección 5.

## 5. Selección real y justificación formal

La tecnología **efectivamente implementada** en el repositorio es la **A4**:

> **React + Vite** (frontend), **Python + FastAPI** (backend), **Firebase Cloud Firestore** (persistencia), **Firebase Admin SDK** (acceso servidor), **python-dotenv** (configuración) y **Pytest** (pruebas).

**Firebase Authentication NO está implementado en el código actual** (no existe módulo de login, ni tokens, ni control de roles por usuario); se documenta como componente **propuesto/pendiente** en iteraciones futuras (ver documento 06, RF-10). La persistencia real se realiza con las credenciales de service account del Admin SDK desde el backend.

### 5.1 Justificación por eje

| Eje | Justificación |
| --- | --- |
| **Arquitectura hexagonal** | La estructura `presentation` → `business` → `data` con puertos (interfaces de repositorio) y adaptadores (repositorios Firestore) ya está implementada y es independiente del proveedor de datos. FastAPI y Pydantic encajan naturalmente como adaptadores de entrada. |
| **Capacidades del equipo** | El equipo del PFA domina Python, desarrollo web y pruebas automatizadas en el contexto académico. Firestore elimina la administración de una base de datos local/servidor. |
| **Facilidad de desarrollo** | FastAPI ofrece validación Pydantic, serialización automática de modelos y OpenAPI/Swagger sin configuración adicional. Vite arranca un entorno de desarrollo con proxy a la API en segundos. |
| **Escalabilidad** | Firestore escala automática y horizontalmente sin aprovisionar servidores; el backend FastAPI es stateless y escalable (Uvicorn). |
| **Costos** | El plan sin costo (Spark/Gratuito) de Firebase cubre holgadamente el volumen académico del MVP; no hay servidores propios ni licencias. |
| **Mantenimiento** | La base administrada se encarga de backups, replicación y operación. La capa de dominio pura permite probar reglas de negocio con repositorios en memoria (86 pruebas). |
| **Integración con Firebase** | `firebase_admin` ofrece SDK oficial para inicializar con service account y acceder a Firestore (colecciones vehiculos, pedidos y asignaciones) de forma estable. |
| **Eficiencia de recursos** | Backend y frontend consumen recursos solo durante la solicitud (FastAPI async + hosting serverless de Firebase); no hay servidores ociosos, reduciendo el consumo energético (alineado con Eco-Design). |
| **Contexto académico** | Presupuesto limitado del PFA (CO-07 del doc. 04), plazo de 14 semanas en 4 iteraciones (doc. 02) e iteraciones incrementales favorecen herramientas de adopción rápida y cero infraestructura local. |
| **Crecimiento futuro** | La arquitectura permite sumar Firestore Collections nuevas, autenticación (Firebase Authentication), y servicios de rutas/tráfico sin reescribir el núcleo de dominio. |

## 6. Conclusión

La alternativa **A4** (Python + FastAPI, React + Vite, Firebase Cloud Firestore, Firebase Admin SDK, python-dotenv y Pytest) obtiene el mayor puntaje de la evaluación (46/50) y es **exactamente la tecnología verificada en el repositorio**, por lo que la selección documental coincide con la implementación. Las demás alternativas se descartan por costo de infraestructura, curva de aprendizaje, consumo energético y menor sintonía con el perfil académico del equipo.
