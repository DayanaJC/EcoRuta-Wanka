## 1. Objetivo del documento

Este documento presenta las tecnologías seleccionadas para desarrollar EcoRuta Wanka y explica los criterios utilizados para elegirlas.

La selección considera el tipo de proyecto, el tamaño del equipo, el presupuesto académico, el plazo de desarrollo, la necesidad de trabajar con una aplicación web, el uso de servicios en la nube y la integración con servicios externos de optimización de rutas y mapas.

> **Control de cambios:** durante el Sprint 1 el equipo reevaluó el stack inicial (Python + FastAPI, React + Vite y Firebase Cloud Firestore). El cambio se registra como **CC-01** en el [Registro de control de cambios](../04%20Seguimiento_control/01%20Registro%20de%20control%20de%20cambios%20V_1_2_0.md).

El stack tecnológico se organiza de acuerdo con la **arquitectura cliente-servidor** definida para el proyecto, aplicando internamente el patrón **MVC con capa de servicios** y una **API REST** entre el cliente y el servidor:

```text
CLIENTE                                   SERVIDOR
Vista (Next.js)  ── API REST (JSON) ──►   Controlador (Express)
                                               ↓
                                          Modelo: Servicios → Repositorios
                                               ↓                    ↓
                               API de optimización de rutas    Neon (PostgreSQL)
```

## 3. Alternativas tecnológicas

La evaluación inicial (04/09/2026) comparó Node.js + Express + React + MongoDB, Python + FastAPI + React + PostgreSQL y Python + FastAPI + React + Firestore, y seleccionó esta última.

Durante el Sprint 1 el equipo identificó tres hechos que motivaron una nueva evaluación:

1. **La optimización de rutas se realizará mediante una API externa** en lugar de desarrollar un algoritmo propio. El backend pasa a ser principalmente un orquestador de llamadas HTTP a servicios externos, que devuelven y reciben JSON.
2. **El modelo de datos es relacional:** pedidos, vehículos, asignaciones y rutas se relacionan entre sí, y el documento *11. Base de datos* ya aplicaba normalización (1FN, 2FN y 3FN). Una base de datos relacional permite garantizar esas relaciones con claves foráneas.
3. **Usar un solo lenguaje (JavaScript) en el cliente y el servidor** reduce la curva de aprendizaje de un equipo de dos integrantes.

Las alternativas reevaluadas son:

| Alternativa | Backend            | Frontend     | Base de datos            |
| ----------- | ------------------ | ------------ | ------------------------ |
| A1          | Python + FastAPI   | React + Vite | Firebase Cloud Firestore |
| A2          | Python + FastAPI   | Next.js      | Neon (PostgreSQL)        |
| A3          | Node.js + Express  | Next.js      | Neon (PostgreSQL)        |

La alternativa **A3** fue seleccionada.

## 5. Stack tecnológico seleccionado

### 5.1 Frontend (Vista)

**Next.js (React)**

Se utilizará para desarrollar la interfaz web del sistema. Next.js está construido sobre React, por lo que los componentes desarrollados con React en el Sprint 1 pueden reutilizarse.

Sus principales funciones son:

* Mostrar información de vehículos y pedidos.
* Permitir la interacción de los usuarios con el sistema.
* Mostrar las rutas generadas sobre un mapa.
* Presentar indicadores y reportes.
* Facilitar la navegación entre las diferentes funcionalidades.

| Tecnología               | Uso                                                              |
| ------------------------ | ---------------------------------------------------------------- |
| Next.js                  | Framework de la interfaz web (React, enrutamiento y compilación). |
| React                    | Componentes reutilizables de la interfaz.                        |
| JavaScript               | Lenguaje utilizado para el desarrollo del frontend.              |
| Leaflet + OpenStreetMap  | Visualización de rutas y pedidos en un mapa (RF-04).             |
| ESLint                   | Revisión y control de calidad del código.                        |

---

### 5.2 Backend (Controlador y Modelo)

**Node.js + Express**

Express se utilizará para desarrollar la API REST que conecta el frontend con la información almacenada y con los servicios externos de rutas.

Sus principales funciones son:

* Exponer los endpoints de la API REST.
* Validar la información recibida.
* Aplicar las reglas de negocio.
* Gestionar vehículos, pedidos, asignaciones y rutas.
* Solicitar la optimización de rutas a la API externa y aplicar los factores de tráfico.
* Conectar los servicios con los repositorios de datos.

| Tecnología  | Uso                                                              |
| ----------- | ---------------------------------------------------------------- |
| Node.js     | Entorno de ejecución del backend (JavaScript).                   |
| Express     | Desarrollo de la API REST (rutas y controladores).               |
| Zod         | Validación de los datos de entrada y salida.                     |
| Prisma ORM  | Acceso a la base de datos, modelos y migraciones.                |
| OpenAPI     | Documentación de los endpoints de la API.                        |

---

### 5.3 Base de datos

**Neon (PostgreSQL serverless)**

Neon es un servicio administrado de PostgreSQL en la nube, con un plan gratuito adecuado para el proyecto académico.

Permitirá almacenar información relacionada con:

* Vehículos.
* Pedidos.
* Asignaciones.
* Rutas y el orden de sus paradas.
* Conductores.
* Preferencias.
* Factores de tráfico.
* Usuarios y roles.

Ventajas para el proyecto:

* Garantiza las relaciones entre entidades mediante **claves foráneas**.
* Permite **transacciones**, por ejemplo al generar una ruta y actualizar el estado de sus pedidos al mismo tiempo.
* Ofrece **ramas (branches)** de la base de datos para separar los datos de desarrollo y de pruebas.
* Reduce la necesidad de configurar y mantener un servidor de base de datos propio.

---

### 5.4 Servicios externos de rutas y mapas

EcoRuta Wanka **no desarrolla un algoritmo propio de optimización**. Utiliza servicios especializados mediante sus APIs y añade una capa propia de ajustes para el contexto de Huancayo.

| Servicio                          | Uso                                                                                                        |
| --------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| OpenRouteService – Optimization   | Calcula el orden óptimo de visita y el reparto de pedidos entre vehículos (motor VROOM), considerando capacidad, ventanas de entrega, tiempos de servicio y turnos. |
| OpenRouteService – Directions     | Obtiene el trazado de la ruta sobre calles reales, la distancia y el tiempo estimado.                      |
| Nominatim (OpenStreetMap)         | Convierte direcciones en coordenadas (geocodificación). En Huancayo ofrece mejores resultados que el geocodificador de OpenRouteService. |
| Leaflet + OpenStreetMap           | Muestra el mapa, los pedidos y las rutas en el frontend.                                                   |

**Capa propia: factores de tráfico.** Los servicios de rutas calculan los tiempos con velocidades promedio de las vías y **no consideran el tráfico en tiempo real**. Para acercar las estimaciones a la operación real, EcoRuta Wanka registra **factores de tráfico** por franja horaria y tipo de día (por ejemplo, hora punta en días laborables). Antes de solicitar la optimización, el backend ajusta el factor de velocidad de cada vehículo según la franja de su salida. Estos factores son estimaciones configurables y no reemplazan una medición real del tráfico.

**Consideraciones del plan gratuito de OpenRouteService** (plan *Standard*):

* Hasta 500 optimizaciones y 2 000 consultas de rutas por día.
* Hasta 3 vehículos por solicitud de optimización.
* Existe un plan *Collaborative* gratuito para proyectos académicos con límites mayores, que se solicita con el correo institucional.

## 6. Relación con la arquitectura

EcoRuta Wanka utiliza una **arquitectura cliente-servidor**. El cliente (navegador) se comunica con el servidor mediante una **API REST**. Internamente se aplica el patrón **MVC con capa de servicios**:

| Parte del MVC   | Responsabilidad                                                     | Tecnología                         | Ubicación                    |
| --------------- | ------------------------------------------------------------------- | ---------------------------------- | ---------------------------- |
| **Vista**       | Pantallas con las que interactúa el usuario.                        | Next.js + React + Leaflet          | `frontend/`                  |
| **Controlador** | Recibe las solicitudes de la API, valida la entrada y responde.     | Express + Zod                      | `backend/src/controllers/`   |
| **Modelo**      | Servicios con las reglas de negocio e integración con APIs externas. | Node.js                            | `backend/src/services/`      |
|                 | Repositorios de acceso a datos.                                     | Prisma ORM + Neon                  | `backend/src/repositories/`  |

Esta separación permite que cada parte tenga una responsabilidad definida y facilita el mantenimiento del sistema.

## 7. Justificación del stack seleccionado

### Uso de APIs de optimización en lugar de un algoritmo propio

Desarrollar un algoritmo de optimización de rutas (problema de ruteo de vehículos con capacidad y ventanas de tiempo) requiere un esfuerzo que excede el plazo del PFA. OpenRouteService ofrece este cálculo sobre calles reales con un plan gratuito. El trabajo del backend consiste en preparar los datos, llamar a la API, aplicar los factores de tráfico e interpretar la respuesta. Node.js está diseñado para este tipo de operaciones de entrada y salida (llamadas HTTP asíncronas con JSON).

### Mejora sobre la API: factores de tráfico

La API de optimización no considera el tráfico. EcoRuta Wanka añade factores de tráfico configurables por franja horaria, lo que permite obtener tiempos estimados más cercanos a la realidad de Huancayo sin desarrollar un motor propio.

### Un solo lenguaje

El frontend y el backend se desarrollan en JavaScript. Esto reduce la curva de aprendizaje, permite compartir esquemas de validación y facilita que ambos integrantes trabajen en cualquier parte del sistema.

### Base de datos relacional

Neon (PostgreSQL) se ajusta al modelo de datos normalizado del proyecto, garantiza la integridad de las relaciones mediante claves foráneas y permite consultas que combinan pedidos, vehículos, asignaciones y rutas.

### Costo

Neon, OpenRouteService, Nominatim y Vercel ofrecen planes gratuitos suficientes para el alcance académico del proyecto. El frontend y el backend se publican en Vercel (CC-02).

### Mantenibilidad

La separación en Vista, Controlador y Modelo (servicios y repositorios) permite realizar cambios en una parte del sistema sin modificar innecesariamente las demás.

### Adecuación al proyecto

El stack seleccionado permite cubrir las principales necesidades de EcoRuta Wanka: gestión de vehículos, pedidos, asignaciones, rutas optimizadas, visualización en mapa, conductores, preferencias, indicadores y reportes.

## 9. Conclusión

El stack seleccionado para EcoRuta Wanka está conformado por **Next.js para el frontend, Node.js + Express para el backend y Neon (PostgreSQL) para la persistencia de datos**, organizado en una **arquitectura cliente-servidor** con el patrón **MVC con capa de servicios** y comunicación mediante **API REST**.

La optimización de rutas se realiza mediante la **API de OpenRouteService**, a la que el sistema añade **factores de tráfico** propios. De esta manera el equipo concentra su esfuerzo en las reglas de negocio de WankaLogística S.A.C. y en la experiencia del usuario, en lugar de desarrollar un motor de optimización desde cero.
